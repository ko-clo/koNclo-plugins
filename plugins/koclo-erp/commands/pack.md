# /pack — Context Pack 작성 (강의 17강)

작업: `$ARGUMENTS`

> **이 커맨드는 코드를 수정하지 않는다.** 작업면을 고정하고 사용자 승인을 받는 것이 목적이다.
> 강의 17강: *"Context Harness 가 먼저, 수정은 나중."*

---

## 왜 쓰나

Claude 가 엉뚱한 파일을 고치는 원인은 설명 부족이 아니라 **작업면이 안 잡혀서**다(17강).
더 긴 설명을 붙이기 전에 아래를 먼저 한다.

## 절차

### 1. 파일 후보 좁히기 — 먼저, 반드시

**최대 5개.** 각각 왜 관련 있는지 한 줄, 수정 가능성 높은 순.

- 넓게 탐색해야 하면 `Explore` 서브에이전트에 위임한다 — 탐색 로그가 메인 컨텍스트를 오염시키지 않는다(17강)
- 관련 탭이 있으면 해당 스킬(`vmd`/`payrate`/`retail-reorder` 등)의 매핑을 먼저 본다
- **5개로 못 좁히면 팩을 쓰지 말고 탐색을 더 하라.** 못 좁힌 채 쓰는 팩은 무의미하다

### 2. 도메인 메모리 확인

`UserPromptSubmit` 훅이 이미 `[MEMORY RECALL]` 을 주입했을 것이다.
`*-feedback.md` 에 이 작업과 관련된 F 교훈이 있으면 **Completion Criteria 에 반영**한다.

### 3. 템플릿 채우기

`.claude/context-pack.template.md` 를 그대로 쓴다. 빈칸을 남기지 마라 —
해당 없으면 **"해당 없음"** 이라고 적는다(모르는 것을 지어내는 것보다 낫다).

특히:
- **Do Not Touch** — `init.sql`, 주문장 생성기, `.env`/`secrets/**` 는 기본 포함
- **Verification** — `CLAUDE.md` §7 의 실제 명령. **이 레포에 pytest 는 없다.**
  검증 스크립트가 없으면 "없음"이라고 적는다
- **Completion Criteria** — "잘 동작한다" 금지. 관찰 가능한 조건으로

### 4. 저장

`.omc/drafts/context-pack-<슬러그>.md` 에 저장한다(커밋 대상 아님).

### 5. 승인 받고 멈춘다

팩을 사용자에게 보여주고 **명시 승인 전까지 코드를 수정하지 않는다.**
사용자가 범위를 승인한 뒤에 구현으로 들어간다.

## 오염됐을 때 (17강 재설계)

세션이 폐기된 가설로 오염됐으면 더 긴 설명이 아니라 **팩 교체**다:

1. "이전 가설은 폐기한다" 명시
2. 새 팩으로 재시작 — 파일 후보부터 다시 좁힌다
3. 수정 전 계획을 받고 사람이 승인
4. 수정 후 focused test 먼저, 전체는 merge 후

## 금지

- 팩 없이 "일단 고쳐보고" 시작하는 것
- 후보를 못 좁혔는데 팩을 쓰는 것
- 승인 전 코드 수정
- Verification 에 이 레포에 없는 명령(`pytest`)을 적는 것
