# Post Verification

> 구현 완료 직후 "동작할 것 같다"를 "검증했다"로 바꾸는 마감 게이트다.
> 변경을 새로 설계하지 않는다. 이미 만든 변경이 요청 의도, 입력/출력 계약, 예외 처리, 로깅, 회귀 위험을 통과했는지 증거로 확인한다.

## 0. 시작 전 확인

1. `CLAUDE.md`와 관련 skill을 따른다.
   - 탭 개발/Vue/API 분리: `dev-blueprint`
   - 브랜치/PR 리뷰: `code-review` 또는 `/pr-review`
   - 인입 포맷: `ingest-guard`
   - 도메인 탭: `vmd`, `payrate`, `best-products`, `auto-payment-cycle`, `order-audit`, `order-cycle`
2. `git status`와 변경 파일 목록을 확인해 이번 작업 범위와 기존 더티 파일을 분리한다.
3. 사용자의 원요청과 수용 기준을 1-2문장으로 복원한다.

## 1. 검증 계획

변경 파일을 아래 축으로 분류하고, 해당 축만 검증한다.

| 변경 축 | 필수 확인 |
|---|---|
| UI | 렌더, 인터랙션, 로딩/빈/오류 상태, 콘솔 에러, 다른 탭 라우팅 |
| API/router | 요청 파라미터 검증, 정상 응답 shape, 오류 응답, 라우터 import smoke |
| service/계산 | 정본 산식, 경계값, 빈 데이터, 중복/누락, 반례 |
| DB/SQL/ingest | 쓰기 전 검증, 멱등성, UNIQUE/FK/인덱스, 부분 저장 방지 |
| 배치/cron/NAS | 로그, 락, 산출물, dev/운영 경계, 승인 필요 작업 |
| 설정/보안 | 비밀값 노출, 권한 약화, 환경별 차이, rollback 가능성 |

## 2. 입력 체크

반드시 실제 입력 경로 기준으로 확인한다.

- 필수값 누락, 빈 문자열, `null`, 0, 음수, 잘못된 날짜/기간 역전.
- 목록/필터/탭/토글 등 UI 입력 상태 변경.
- 중복 요청, 재실행, 기존 데이터가 있는 상태.
- 파일 인입이면 컬럼 구조, 파일명 패턴, 빈 파일, 외래 양식.
- 사용자가 보낸 값이 조용히 전체 범위나 기본값으로 폴백하지 않는지 확인한다.

## 3. 출력 체크

정상 결과와 실패 결과를 나눠 확인한다.

- 성공 응답: 필드명, 타입, 단위, 날짜/기간, 합계, 정렬, 빈 값 표현.
- 화면 출력: KPI, 테이블, 차트, 이미지/모달, sticky/scroll, 모바일/폭 좁은 상태.
- 저장/인입 결과: 건수, 날짜 범위, 중복 흡수, 기존 데이터 보존.
- 오류 출력: 사용자 메시지는 안전하고, 내부 진단 정보는 로그에 남는다.
- 기존 oracle이 있으면 기존 HTML/리포트/정본 쿼리와 수치를 대조한다.

## 4. 예외 처리 체크

- 외부 API, DB, 파일, 네트워크, Docker/NAS 호출 실패가 명시적으로 처리되는지 확인한다.
- 처리 가능한 예외만 잡고, 처리할 수 없는 예외는 맥락을 보존해 상위로 전달한다.
- 예외를 삼키거나 빈 결과로 위장하지 않는다.
- 실패 중간에 부분 저장, 부분 삭제, 처리완료 마킹이 남지 않는지 확인한다.
- UI는 실패 시 무한 로딩이나 빈 화면으로 멈추지 않는다.

## 5. 로깅 체크

- 실패 로그는 원인 추적에 필요한 식별자, 날짜, 단계, 파일명, 건수를 포함한다.
- 성공 로그는 운영 판단에 필요한 상태 변화만 남긴다.
- 비밀번호, 토큰, DSN, 개인정보, 원본 운영 데이터 덤프를 로그나 최종 응답에 노출하지 않는다.
- 같은 의미의 로그를 여러 곳에 중복 추가하지 않는다.

## 6. 실행 검증

가장 좁은 검증부터 실행하고, 변경 위험에 따라 넓힌다.

1. 정적/구문 확인: import smoke, `ast.parse`, `bash -n`, 타입/린트 중 해당되는 것.
2. 단위 검증: 계산 함수, format guard, helper, edge case.
3. API 검증: 정상/오류 요청, 응답 shape, 400/500 여부.
4. UI 검증: 렌더, 상호작용, 콘솔 에러 0.
5. dev 서버 검증: 필요하면 `/server-test`로 dev 오버레이 후 확인하고 `/server-clear`로 원복한다.
6. 리뷰 검증: merge 전 또는 영향 범위가 넓으면 `/pr-review <브랜치>`로 독립 리뷰를 받는다.

Docker, NAS, DB 쓰기, 배포, 마이그레이션, git commit/push는 `CLAUDE.md` 승인 규칙을 따른다.

## 7. 반례 루프

아래 중 관련 있는 반례를 최소 1개 이상 시도한다.

- 빈 데이터, 데이터 1건, 대량 데이터.
- 날짜 역전, 범위 밖 날짜, 미래 날짜.
- 중복 실행, 재시도, 이미 처리된 파일/행.
- product/store/supplier 매칭 실패.
- 네트워크/DB/파일 없음.
- 공유 자산 변경 후 인접 탭 회귀.

반례가 실패하면 수정 후 영향받은 검증을 다시 실행한다. 같은 blocker가 3회 반복되면 완료가 아니라 blocker로 보고한다.

## 8. 최종 판정

판정은 셋 중 하나만 사용한다.

- `PASS`: 수용 기준과 핵심 반례가 증거로 통과.
- `FAIL`: 구현 결함 또는 회귀가 확인됨.
- `INCOMPLETE`: 환경/승인/데이터 부족으로 핵심 검증이 남음.

## 9. 보고 형식

최종 보고 전에 아래 형식으로 요약한다.

```text
판정: PASS | FAIL | INCOMPLETE
변경 범위: <파일/영역>
입력 체크: <확인한 정상/오류 입력>
출력 체크: <응답/화면/저장 결과>
예외/로깅: <처리 경로와 민감정보 노출 여부>
실행 검증: <명령 또는 수동 확인 + 결과>
회귀/반례: <시도한 반례와 결과>
남은 리스크: <없음 또는 구체적 미검증 항목>
```

검증하지 않은 항목을 검증한 것처럼 쓰지 않는다. `py_compile`만으로 import smoke를 대체하지 않는다. "should work"는 완료 근거가 아니다.
