# 주문장 검수 스킬

**목적**: 이미 생성된 주문장(.xls)에서 *잘못된/의심스러운 데이터*를 찾고, 특정 품목의
주문수량이 **왜 그 값으로 나왔는지** 산식을 역추적한다. 주문장을 새로 만들지 않는다.

**필독(맥락)**: `domain/order.md` · `domain/order-feedback.md` · `service/order-architecture.md`
**관련 스킬**: 생성은 `order-cycle`(자동) / `/order-manual`(수동). 본 스킬은 *검수만*.

---

## 검수 도구 (읽기 전용)

`backend/scripts/audit_order_xls.py` — DB·NAS 없이 .xls + 비고(2w/점수/상태/태그)만으로 검증.
현재고는 .xls 에 없으므로 주문 산식에서 **역산한 추정값**으로 표시한다.

```bash
# 1) 이상치 스캔 (폴더 또는 단일 파일)
python3 backend/scripts/audit_order_xls.py scan <폴더|파일> [--store 09]

# 2) 특정 품목 주문수량 산식 역추적
python3 backend/scripts/audit_order_xls.py explain <파일> --product 레시피반팔 [--color 스카이]

# 3) 두 산출물(빌드/시스템) 동일 품목 비교
python3 backend/scripts/audit_order_xls.py compare <파일A> <파일B> [--product 레시피반팔]
```

산출물 위치(로컬 마운트): `/Volumes/자동주문/cache/주문장_업로드_new/주문장_YYYYMMDD/*.xls`

## 주문수량 산식 (검수 기준)

`order_v8_2_rebuild_FULL.py` + `auto_order_db.py` 의 확정 로직. 검수 스크립트 상수와 일치해야 함.

1. **기본 주문량** = `max(0, 안전재고(2주판매 구간) − 현재고)`
   - 안전재고 테이블(구간 → 안전재고): `(11~16)→8`, `(17~20)→13`, `(21~24)→18`, `(25~49)→22` …
   - 50+ 구간은 `min_stock` 미달 시에만 주문, 최대 `HIGH_SALES_ORDER_CAP=35`.
2. **상위5% 강화**: `점수 ≥ gc` 인 항목만. `gc` = **그 산출물 후보(점수>0) 점수의 95백분위** (동적).
   - 강화수량: 2w≤20 → 2주판매분까지 채움(`max(0, 2w−현재고)`), 21~29 → 80%, 30~49 → 75% (재고 게이트 60%).
   - 최종 수량 = `max(기본 주문량, 강화수량)`.
3. **과락(주문 0)**: 악성재고(30일+) / 점수 하위 30% / 조건부 LR.
4. **면제(베스트·샘플·신상)**: 과락 우회, 재고 부족분만 주문.

## 알려진 이상 패턴 (검수 체크리스트)

> 새 패턴 발견 시 아래 표에 즉시 추가. (이 스킬은 "계속 변경·추가" 전제)

| 증상 | 원인 | 확인 방법 / 판정 |
|---|---|---|
| **잘 팔리는데 주문 1장** (예: 레시피반팔 스카이 2w17·현재고12 → 1) | 안전재고 (17~20)=13 이 실판매보다 낮음 + 점수가 그 매장 상위5% 컷오프 미달 → 강화 미적용 | `explain` 로 `안전재고−현재고=기본주문`, `점수<gc` 확인. **산식대로면 버그 아님 = 정책 이슈** |
| **같은 품목인데 산출물마다 수량 다름** (노랑 2 vs 5) | 상위5% 컷오프 `gc`가 후보 모집단 의존 상대 백분위 → 모집단 다르면 경계 점수 품목의 강화 on/off 뒤집힘 | `compare` 로 두 산출물 `gc` 비교. **`gc` 상이 + 경계점수면 이게 원인** |
| 수량=0 행이 과반 | `통과(재고ok)`·`재고충분` 행이 .xls 에 포함됨(설계). 주문 아님 | `scan` 의 `수량0 NN%`. 주문 행만 보려면 비고 `주문/통과주문/강화` |
| 강화 태그인데 점수<컷오프 | 산출 시점 모집단과 표시 불일치 가능 | `scan` 의 `강화태그<컷오프` 플래그 |
| 사입처/품명 공백 | 정규화(pm_suppliers) `supplier_id` NULL/미매칭 → `s.name=''` (현재 시스템) | `scan` 의 `사입처공백`. DB 매칭 추적 필요 |
| 중복행 | 미송 병합/추출 중복 | `scan` 의 `중복행` |
| **베스트/급상승인데 안전재고만큼만 주문** (예: 타이레이어드셔츠 연회 1주판매8·재고4 → 2) | ① 안전재고는 *2주누계* 기준이라 급상승(전량 최근1주) 반영 못함(2w8→안전재고6). ② **베스트(KA/TB) 면제는 과락만 우회·수량은 안전재고−현재고로 제한**. ③ 2주판매분까지 채우는 상위5% 강화는 점수<gc로 미적용 | `explain` 통과주문(베스트)+`max(0,안전재고−현재고)` 확인. **안전재고<실판매 + 강화컷오프 미달 정책 이슈** (베스트 면제로도 수량 안 늘어남) |
| **최근입고 30일+ 인데 주문됨** (예: 비비PT 백메란지 입고5.18·36일 → 2) | 악성재고(`DEAD_STOCK_DAYS=30`)지만 **창고복귀 급상승 오버라이드**(line1527)로 컷 해제. C1=`2주전주간≥2 & 1주≥3 & 1주≥2주전×2`, C2=`2주전주간=0 & 1주≥4`(무판매→급등). 해제 후 안전재고−현재고로 정상 주문 | DB로 `sales_daily` 주별 분포 확인(s1w, s2w_prev). C1/C2 충족 시 **의도된 동작(다시 팔리는 상품 보충), 버그 아님** |
| **신상(오늘 입고)인데 과락** (예: 더블포켓다잉반팔티 그레이 2w1·점수25 → 0) | 신상 면제는 `is_new = 최초사입일경과일 ≤ 21`. **사입(purchase_daily) 기록이 0건**이면 `first_purchase_date=None → first_age_days=999(else 기본값)` → is_new=False 로 *무이력을 헌상품(999일)으로 뒤집음*. 판매만 있어 후보엔 들지만 점수 콜드스타트 바닥 → 하위30% 과락. 악성재고 과락엔 `last_purchase_date is None → 면제`(F19 line1521) 가드가 있으나 **점수 과락엔 그 가드가 없음** | DB 대조: `purchase_daily` 해당 product_id 사입 0건 + `sales_daily` 판매만 있음 확인. 입고가 아직 미인입(파이프라인 비대칭)이거나 product 신규생성만 된 상태. **신상 판정이 사입기록 의존 → 입고 미인입 시 신상보호 전부 무력화 = 로직 갭(정책+파이프라인)** |

## 시스템 구분 (혼동 주의)

`order_paper/old` 같은 비교 대상이 **현재 시스템의 이전 빌드가 아닐 수 있음**.

| | 현재 (koclo-erp) | 레거시 (koclo-erp-legacy) |
|---|---|---|
| DB | `KOCLO_ERP_DB_DSN` (testerp/_dev, **pm_suppliers 정규화**) | `TESTERP_DB_DSN`(5434, `products.supplier_name` 직접) |
| 사입처 조회 | `LEFT JOIN pm_suppliers s ON s.id=p.supplier_id`, `GROUP BY s.name` | `p.supplier_name` 직접 |
| 미송 병합 | xls write 직전 병합 있음 | 없음 |
| 안전재고·기본주문·상위5% 강화 코드 | **두 시스템 동일** | **동일** |

→ 두 산출물 비교 시 **어느 시스템/DB 산출인지 먼저 확정**. 코드가 같아도 DB가 다르면
모집단·점수 분포가 달라 `gc`·강화 결과가 갈린다.

## 검수 절차

1. `scan` 으로 전체 매장 이상치 훑기 (수량0 비율·CAP·공백·중복·강화모순).
2. 의심 품목은 `explain` 으로 산식 역추적 → **"산식대로(정책)" vs "입력 데이터 오류" vs "강화 컷오프 효과"** 분류.
3. 다른 산출물이 있으면 `compare` 로 `gc`·수량 차이 원인 분리.
4. 입력 데이터(현재고·2주판매) 자체 의심 시 → DB 대조 필요. `KOCLO_ERP_DB` 는 NAS(`koclo_erp-app`),
   조회하려면 `/nas on` 필요(읽기 전용 쿼리). 결과는 추정 현재고와 대조.
5. 결론: 코드 결함 / 정책(안전재고·컷오프) / 입력 데이터 오류 중 무엇인지 한 줄로 보고.

## 절대 원칙

- **읽기 전용** — 주문장 재생성·운영 DB 변경 금지. 생성이 필요하면 `order-cycle`/`/order-manual`.
- 검수 스크립트 상수(안전재고 테이블·상위5% 산식)는 `order_v8_2`/`auto_order_db` 와 항상 동기화.
- 새 이상 패턴은 위 체크리스트에 누적.
