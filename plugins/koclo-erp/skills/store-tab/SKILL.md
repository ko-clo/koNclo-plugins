# store-tab — 매장(현장)용 간소화 탭 생성기

> **새 기능을 만드는 스킬이 아니다.** 이미 있는 본사용 탭에서 **매장이 실제로 쓰는 것만 남긴**
> 별도 뷰를 조립해 `[매장관리]` 그룹에 붙인다. 데이터·판정·API 는 전부 원본과 공유한다.
> 탭 개발 표준은 `dev-blueprint`(§1 불변규칙·§4 UX·§6 검증게이트를 그대로 상속), 병행 뷰 선례는 `mobile-blueprint`.
> 원본 탭의 판정 규칙을 바꾸는 것은 **이 스킬의 범위 밖** — 그 탭 전담 에이전트 소관이다.

## 0. 탭 원칙 (이 스킬의 존재 이유 — 모든 결정의 상위 기준)

1. **사용이 편리** — 매장 직원이 설명 없이 1화면에서 오늘 할 일을 안다.
2. **디자인이 직관적** — 숫자를 해석하게 만들지 않는다. 결론과 사유를 문장으로 보여준다.
3. **필요 없는 기능 제거 (가장 중요)** — 매장이 쓰지 않는 것을 덜어낸다.
   어떤 요소든 화면에 두려면 "이걸 보고 매장이 무슨 행동을 하는가"에 한 줄로 답할 수 있어야 한다.
   답이 없으면 뺀다.

> **축소의 깊이는 요청자가 정한다 — 지정이 있으면 그것이 §1·§2 보다 우선한다.**
> "필요 없는 것을 빼라"를 "원본을 최소 화면으로 재설계하라"로 확대 해석하지 않는다.
> **서브탭·컬럼·표를 없애라는 지시가 없었다면 없애지 않는다.** 요청자가 범위를 말하지 않은 경우에만
> §1 을 기본값으로 적용하고, 그때도 무엇을 뺐는지 plan 에 적어 확인받는다.

## 1. 기본 제외 목록 (요청자가 범위를 지정하지 않았을 때의 기본값)

> **이 표는 상한이 아니라 출발점이다.** 요청자가 "이 영역은 원본 그대로 두라"고 하면 그 지정이 이긴다.
> 표를 근거로 요청자가 남기라고 한 것을 빼지 않는다.

| # | 제외 대상 | 원본 탭의 실제 예 | 사유 |
|---|---|---|---|
| E1 | **상단 탭간이동 버튼(서브탭 바)** | `SubTabLayout` 의 `.subtab-bar-content` | 매장은 본사 탭 사이를 오갈 일이 없다. **라우트를 `SubTabLayout` 없이 등록**해 원천 차단(§3-2) |
| E2 | **페이지 헤더(제목·부제)** | `.page-header` | 사이드바에 이미 있다. 세로 공간 낭비 |

| E4 | **전사 합계·집계 컬럼** | 전매장 KPI 카드 · 합계행 · 누적/평균 · 보유매장수 · 매장수 | 본사 의사결정용 지표 |

| E6 | **시뮬레이션·정책 파라미터 조정** | 반납 시뮬 박스(기한·점수 컷오프) · 안전재고 설정 · 기간/가중치 입력 | 본사 정책. 매장이 바꾸면 정본이 흔들린다 |
| E7 | **생성·재계산·배치 트리거** | 주문장 생성 · 풀 재계산 · 캐시 클리어 · 배치 재실행 | 운영 사고 경로. 매장 화면에 두지 않는다 |
| E8 | **운영/디버그 표시** | 데이터 상태 · 빌드 이력 · stale 경고 배너 · raw JSON · 커버리지/원천점검 | 본사·개발 관측용 |
| E9 | **대량 편집·전송 워크플로** | 워크북 시트 편집 · 마스터시트 전송 · 다중선택 이동/복사 | 본사 워크플로 전체가 딸려온다 |
| E10 | **차트·추이 그래프** | 주별 지급 추이 · 월별 시계열 | 액션으로 이어지지 않으면 장식이다 |
> 위 항목을 **넣어야 할 사유**가 있으면 plan 에 적고 승인받는다. 조용히 포함하지 않는다.
> 반대로 요청자가 남기라고 한 것을 이 표를 근거로 빼지도 않는다.

## 2. 남길 것 (판단 기준)

- **매장이 오늘 할 일** — 대상 행과 그 **사유**. 사유는 결론이 드러나게 표기한다.
- **상품 식별에 필요한 것** — 이미지 · 품명 · 컬러/사이즈 · 현재고 · 최근 판매.
- **매장이 실제로 수행하는 액션** — 체크/저장·엑셀 등. 매장이 하지 않는 본사 액션만 뺀다.
- **검색·정렬** — 목록이 길면 남긴다.

**규모**: 고정 상한을 두지 않는다. 다만 **원본보다 단순해야** 한다 —
plan 에 **원본 대비 무엇이 줄었는지**(서브탭·컬럼·버튼 수)를 적어 확인받는다.
요청자가 "원본 그대로"라고 한 영역은 컬럼 수와 무관하게 그대로 둔다.

## 3. 산출물 (매장탭 1개당)

```
frontend/
├── js/views/store/<Tab>StoreView.js   ← 신규. 표현만. 판정·API 는 원본과 공유(import)
├── js/views/<Tab>View.js              ← 무수정 (원본은 한 줄도 건드리지 않는다)
├── js/navTabs.js                      ← 수정: STORE_TABS 에 1행 추가
├── js/app.js                          ← 수정: 라우트 1개 추가 (SubTabLayout 미사용 — §3-2)
├── css/store/<tab>.css                ← 필요 시. `.st-<tab>` 루트 스코프
└── index.html                         ← css 추가한 경우만 `?v=` link 1줄

backend/app/services/role_permission_service.py  ← 수정: TAB_GROUPS 의 "store" 그룹에 1행 추가
.claude/skills/store-tab/SKILL.md                ← 수정: §7 현황 표에 행 추가
```

**위젯·`api.js`·판정 모듈은 원본 것을 그대로 import 한다. 매장탭 전용 API·전용 판정 신설 금지.**

### 3-1. 등록은 반드시 2곳 (한쪽만 하면 탭이 안 보인다)

| 곳 | 파일 | 추가 내용 |
|---|---|---|
| 프론트 | `frontend/js/navTabs.js` `STORE_TABS` | `{ label, route: '/store/<name>', id: 'store-<name>', done: true, sub: '…' }` |
| 백엔드 | `backend/app/services/role_permission_service.py` `TAB_GROUPS` → `id: "store"` | `{"id": "store-<name>", "label": "…"}` |

id 는 **양쪽이 정확히 같아야** 한다(`store-<name>`). 백엔드에 없으면 `allowed_tabs` 에서 빠져 라우트가 튕긴다.

### 3-2. 라우트는 `SubTabLayout` 없이 등록한다 (E1·E2 를 구조로 차단)

```js
// frontend/js/app.js — 매장관리 그룹
{ path: '/store/<name>', component: <Tab>StoreView, meta: { nav: 'store-<name>' } },
```

`SubTabLayout` 으로 감싸면 `STORE_TABS` 가 2개 이상일 때 **상단 탭간이동 바와 페이지 헤더가 자동으로 붙는다.**
직접 등록하면 둘 다 사라지고, 권한 검사(`meta.nav`)와 사이드바 활성 표시는 그대로 동작한다.
**공용 컴포넌트(`SubTabLayout`)는 수정하지 않는다.**

## 4. 절차

### 4-0. 모드·대상 식별
- `/store-tab 생성 <원본탭>` → 신설. `/store-tab 수정 <매장탭>` → 기존 매장탭 변경.
- **인자가 없으면** `frontend/js/navTabs.js` 근거로 목록을 제시하고 **AskUserQuestion 으로 묻는다**(임의 진행 금지).
- 생성인데 이미 같은 원본의 매장탭이 있으면 → **수정임을 먼저 알리고** 범위를 확인한다.

### 4-1. 탐색 (읽기 전용 — 파일 생성·수정 전)
1. **원본 탭 메모리 3종**: `.claude/memory/domain/<tab>.md` · `service/<tab>-architecture.md` · `domain/<tab>-feedback.md`.
2. **원본 View·위젯**: 서브탭 구성, 각 표의 컬럼, 어떤 계산이 위젯 안에 갇혀 있는지.
3. **API**: `frontend/js/api.js` 의 호출 함수 — 매장탭도 **동일 엔드포인트를 재사용**한다.
4. **매장이 실제로 하는 행동**을 원본 화면에서 1~2개 식별한다(여기서 남길 것이 정해진다).
5. **§1 제외표 전수 대조** — 원본의 어느 요소가 E1~E11 중 무엇에 걸리는지 목록화.

### 4-2. Plan 제시 (필수 — 승인 전 파일 생성·수정 절대 금지)
`EnterPlanMode` 로 진입해 아래를 담고 `ExitPlanMode` 로 승인받는다.

- **원본 탭 요약**: 서브탭·표·컬럼 목록.
- **제외/포함 표** — 원본 요소별로 `포함 / 제외(E번호)` + 포함이면 "이걸 보고 매장이 하는 행동":

  | 원본 요소 | 처리 | 매장의 행동 | 근거 |
  |---|---|---|---|
  | 반납대상 목록 | 포함 | 해당 상품을 골라 반납 박스에 담는다 | 탭 목적 |
  | 매장간 비교표 | 제외 | — | E3 |

- **최종 화면 스케치**: 남는 서브탭·컬럼·액션 버튼·검색/필터 + **원본 대비 감소분**.
- **변경 파일 목록**(신규/수정 구분, 수정은 몇 줄인지) + **등록 2곳** 명시.
- **검증 계획**(§5).

**결정 포인트는 AskUserQuestion 으로 확인**(§6).

### 4-3. 구현 (승인 후)
원본 탭 전담 에이전트가 있으면(`<tab>-*-agent`) **표현 이식을 그 에이전트에 위임**한다. 없으면 직접 구현한다.
어느 쪽이든 **원본 View·위젯·service 는 무수정**이 조건이다. 계산이 위젯에 갇혀 재사용이 안 되면
**동작 무변경 추출**만 허용하고, 판정 규칙 변경이 필요하면 그 시점에 멈추고 보고한다.

### 4-4. 검증 → 4-5. 마무리
`dev-blueprint` §6 게이트 + §5 매장탭 전용 게이트를 수행한다. §7 현황 표에 행을 추가하고,
새로 배운 지뢰는 `/learn` 으로 원본 탭의 `<tab>-feedback.md` 에 누적한다.
커밋과 `/server-test` 는 **명시 승인 후에만**.

## 6. 결정 포인트 (plan 단계에서 AskUserQuestion)

1. **축소 깊이** — 원본 구조를 유지하고 본사 chrome 만 걷어낼지, 핵심 화면으로 축약할지.

## 8. 알려진 갭 — 매장 스코프 (반드시 인지하고 작업할 것)

`users` 테이블에 **매장 바인딩이 없다**(`role` 만 존재: admin/manager/manager-jp/viewer).
따라서 **서버측에서 "이 계정은 자기 매장만" 을 강제할 수 없다.**

- 현재 방식: `store_user_context.py` 가 **login_id·email·name 별칭**으로 매장 계정을 식별해
  `/api/auth/me` 에 `store` 컨텍스트와 `allowed_tabs=['store-dashboard']` 를 실어준다.
  프론트는 그 코드로 매장 목록을 1개로 좁힌다. **별칭 매칭이라 정본이 아니다** —
  `users.store_code` 가 생기기 전까지는 임시 방편이고, API 응답 자체는 여전히 전 매장을 담는다.
- 관리자 계정은 화면 상단 **미리보기 매장 선택 UI** 로 매장 화면을 확인한다.
- 이 갭이 §1 E3·E4 를 **더 중요하게** 만든다 — 타 매장 지급율·매출 등 민감 지표는
  권한이 아니라 **화면 구성으로 차단**한다(애초에 매장탭에 담지 않는다).
- 후속 과제(이 스킬 범위 밖): `users.store_code` 추가 + `store` 역할 신설 + API 서버측 매장 필터.
  착수하면 이 절을 갱신한다.
