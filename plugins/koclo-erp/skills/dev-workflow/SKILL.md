# dev-workflow — 개발 작업 3모드 절차

> **요청을 받으면 즉시 코드를 작성하지 않는다.** 먼저 모드를 분류하고, 설계를 제시하고, 승인을 받는다.
> 이 스킬은 **메인 Claude가 따르는 절차서**다. 구현은 기존 탭 에이전트, 리뷰는 `code-review-*`,
> 마감 검증은 `post-verification` 스킬을 **재사용**한다 — 여기서 재서술하지 않는다.
> 강제: `PreToolUse` 훅 `.claude/hooks/design-gate.sh` 가 승인 전 `backend/**`·`frontend/**` 편집을 차단한다.

## 0. 모드 ↔ 전담 에이전트 매핑

| 모드 | 언제 | 설계 담당 에이전트 | 필수 산출물 |
|---|---|---|---|
| **기능추가** | 새 기능·화면·API·DB 구조·워크플로우 신설 | `dev-feature-design-agent` | 흐름 다이어그램·기능정의(입출력/성공/실패/빈데이터/권한)·데이터흐름·API설계·UI설계·테스트계획·구현순서 |
| **기능수정** | 기존 동작·로직·UI·응답·계산식·데이터흐름 변경 | `dev-change-impact-agent` | 기존 동작 조사·수정/제거/추가 위험비교·**변경 대상/비대상**·호환성·회귀 테스트 계획 |
| **버그해결** | 에러·오작동·예외·데이터 불일치 제거 | `dev-bug-triage-agent` | 문제정의 1문장·재현 결과·근거 기반 원인분석·해결방법·**방지책 1개 이상**·검증 계획 |

공통 1단계 조사는 모드와 무관하게 `dev-investigator-agent`(읽기전용)가 맡는다.
구현 후 검증은 `dev-verify-agent`(별도 레인 — 자기승인 금지)가 맡는다.

**모드가 섞인 요청**(예: "이 버그 고치고 필터도 추가해")은 **분리해서 각각 게이트를 태운다.**
한 번에 묶어 승인받지 않는다 — 승인 범위가 흐려진다.

## 1. 작업 흐름과 스텝 배너

```
요청
 └─▶ ① 모드 분류 ──────────── §2  (코드 읽기만, 편집 금지)
     └─▶ ② 조사 ──────────── dev-investigator-agent (읽기전용)
         └─▶ ③ 설계 ──────── 모드별 설계 에이전트 (읽기전용)
             └─▶ ④ 승인 ──── §3 템플릿 출력 → **정지** → 승인 시에만 §4 게이트 개방
                 └─▶ ⑤ 구현 ─ 기존 탭 에이전트 (§5)
                     └─▶ ⑥ 검증 ─ dev-verify-agent + post-verification
                         └─▶ ⑦ 완료 보고 §6 → 게이트 잠금
```

②③ 은 **단일 메시지로 병렬 위임**할 수 있다(조사 결과가 설계의 입력이면 순차).
요청이 작아 조사가 파일 2~3개로 끝나면 ② 를 메인이 직접 해도 된다 — **④ 게이트만은 생략 금지.**

### 스텝 배너 — 모든 스텝은 이 머리를 달고 나온다

사용자는 **지금 몇 번째 스텝인지**와 **그 스텝의 결론**을 본문을 읽기 전에 알아야 한다.
스텝 본문을 배너 없이 출력하지 않는다.

````markdown
---

### ② 조사 요약 — stacking context 가둠
`① 분류 ▸ 【② 조사】 ▸ ③ 설계 ▸ ④ 승인 ▸ ⑤ 구현 ▸ ⑥ 검증 ▸ ⑦ 완료`

> 근본 원인은 z-index 값이 아니라 `.tab-body` 의 transform 이 새 stacking context 를 만든 것.

- `frontend/css/layout.css:88` — transform 진원지
- `frontend/views/InventoryView.js:412` — 모달 마운트 위치
````

네 줄이 한 세트다.

1. **`---` 구분선** — 스텝 사이를 끊는다. 바로 위에 빈 줄을 둔다(앞 문단이 제목으로 오해되지 않게).
2. **`### <번호> <스텝 이름> — <결론>`** — 꼬리(`—` 뒤)에는 **결론**을 적는다.
   스텝 이름을 되풀이하거나("② 조사 요약 — 조사했습니다") 빈칸으로 두지 않는다.
3. **진행 레일** — 인라인 코드 한 줄. 7칸을 **항상 전부** 적고 현재 스텝만 `【 】` 로 감싼다.
4. **`>` 인용 1~2문장 요약** — 그 줄만 읽고도 판단할 수 있게 쓴다. 상세 본문은 그 아래에 둔다.

레일은 아래를 **그대로 복사**한다(칸을 줄이거나 번호를 바꾸지 않는다).

```
`【① 분류】 ▸ ② 조사 ▸ ③ 설계 ▸ ④ 승인 ▸ ⑤ 구현 ▸ ⑥ 검증 ▸ ⑦ 완료`
`① 분류 ▸ 【② 조사】 ▸ ③ 설계 ▸ ④ 승인 ▸ ⑤ 구현 ▸ ⑥ 검증 ▸ ⑦ 완료`
`① 분류 ▸ ② 조사 ▸ 【③ 설계】 ▸ ④ 승인 ▸ ⑤ 구현 ▸ ⑥ 검증 ▸ ⑦ 완료`
`① 분류 ▸ ② 조사 ▸ ③ 설계 ▸ 【④ 승인】 ▸ ⑤ 구현 ▸ ⑥ 검증 ▸ ⑦ 완료`
`① 분류 ▸ ② 조사 ▸ ③ 설계 ▸ ④ 승인 ▸ 【⑤ 구현】 ▸ ⑥ 검증 ▸ ⑦ 완료`
`① 분류 ▸ ② 조사 ▸ ③ 설계 ▸ ④ 승인 ▸ ⑤ 구현 ▸ 【⑥ 검증】 ▸ ⑦ 완료`
`① 분류 ▸ ② 조사 ▸ ③ 설계 ▸ ④ 승인 ▸ ⑤ 구현 ▸ ⑥ 검증 ▸ 【⑦ 완료】`
```

| 스텝 | 헤딩 예시 | 꼬리(`—` 뒤)에 적을 것 | 본문 출처 |
|---|---|---|---|
| ① | `### ① 모드 분류 — 버그해결` | 선택한 모드 이름 | §2 판단 근거 |
| ② | `### ② 조사 요약 — stacking context 가둠` | 조사로 **확정한 사실** 한 마디 | `dev-investigator-agent` 결과 |
| ③ | `### ③ 설계 — 모달을 body 로 teleport` | **채택한 방향** | 모드별 설계 에이전트 결과 + §0 산출물 |
| ④ | `### ④ 승인 게이트 — 승인 대기` | 항상 `승인 대기` | §3 템플릿 |
| ⑤ | `### ⑤ 구현 — InventoryView 등 2파일 수정` | 실제로 바뀐 범위 | 위임 대상·변경 요약(§5) |
| ⑥ | `### ⑥ 검증 — 3/3 통과` | 통과/실패 **수** | `dev-verify-agent` 결과 |
| ⑦ | `### ⑦ 완료 — 모달 노출 정상, 남은 리스크 없음` | 결과 + 남은 리스크 유무 | §6 완료 보고 |

**규칙**

- **한 응답에 여러 스텝**이 들어가면(①②③④ 를 한 번에 낼 때) 배너를 **스텝 수만큼** 단다.
  묶어서 하나로 줄이지 않는다 — 사용자가 어디까지 진행됐는지 세지 못한다.
- **건너뛴 스텝도 배너 한 줄은 남긴다** — `### ② 조사 — 생략(파일 2개로 확정)`.
  조용히 빠뜨리면 절차를 지켰는지 사용자가 확인할 수 없다.
- ④ 는 배너 뒤 본문의 **끝이 승인 질문**이고 거기서 정지한다(§3). 뒤에 ⑤ 배너를 미리 붙이지 않는다.
- 위임한 에이전트의 보고를 **배너 없이 그대로 붙여넣지 않는다** — 메인이 배너를 씌워 relay 한다.
- `/design on` 우회로 열린 세션이라도 **① 배너 하나는 남긴다**(§4).

## 2. 모드 분류 (첫 응답에서 반드시)

아래를 **그대로** 출력한다.

````markdown
---

### ① 모드 분류 — <기능추가 | 기능수정 | 버그해결>
`【① 분류】 ▸ ② 조사 ▸ ③ 설계 ▸ ④ 승인 ▸ ⑤ 구현 ▸ ⑥ 검증 ▸ ⑦ 완료`

> 요청의 "<인용>" 은 <근거> 이므로 **<모드>** 로 분류했습니다.
````

- 모드가 명백하면 **묻지 않고** 바로 ②③ 조사·설계로 이어간 뒤 §3 ④ 게이트에서 함께 승인받는다(왕복 2회 → 1회).
- 모드가 **모호하면 여기서 멈추고** AskUserQuestion 으로 확인한다(텍스트 질문 금지, kernel §2).
  이때도 ① 배너는 먼저 출력하고, 꼬리에 `판단 보류` 라고 적는다.
- 분류가 어려운 경계:
  - "안 되던 걸 되게" = 버그해결 / "되던 걸 다르게" = 기능수정 / "없던 걸 새로" = 기능추가
  - 계산식 변경은 **기능수정**이다(값이 갈리므로 회귀 계획이 핵심).
  - "성능 개선"은 동작 불변이면 기능수정, 새 캐시·테이블 신설이면 기능추가.

## 3. 승인 게이트 템플릿 (코드 작성 전 필수 출력)

````markdown
---

### ④ 승인 게이트 — 승인 대기
`① 분류 ▸ ② 조사 ▸ ③ 설계 ▸ 【④ 승인】 ▸ ⑤ 구현 ▸ ⑥ 검증 ▸ ⑦ 완료`

> <이 방향을 한 문장으로 — 사용자가 이 줄만 읽고 승인 여부를 판단할 수 있게>

선택한 작업 모드: <모드>

조사 요약:
- <한 줄>

구현/수정 방향:
- <한 줄>

선택 이유와 근거:
- 기존 코드 구조 / 데이터 흐름 / 유지보수성 / 테스트 가능성 / 영향 범위 / DRY·KISS·YAGNI

Trade-off:
- 장점:
- 단점:

영향 범위:
- Frontend: / Backend: / DB: / API: / Test: / MCP·Agent: / 기타:

검증 계획:
- <이 레포에 실재하는 명령만> (CLAUDE.md §검증 명령 — pytest 없음)

이 방향으로 코드 작업을 시작해도 될까요?
````

모드별 추가 산출물(§0 표)은 ③ 설계 배너 아래에 두고, ④ 배너에는 위 템플릿만 담는다.
② 조사·③ 설계 배너를 같은 응답에 함께 낼 때도 ④ 는 **별도 배너**로 끊는다.

**금지**
- 빈칸·"추후 확인" 으로 남기기 → 해당 없으면 **"해당 없음"** 이라고 적는다.
- 이 레포에 없는 검증 명령(`pytest`) 적기.
- 승인 전 `backend/**`·`frontend/**` 편집·마이그레이션·커밋·배포. (훅이 차단하지만 **규칙이 먼저다**)
- 내가 덧붙인 부가 제안을 승인 범위에 끼워 넣기 — 사용자가 승인한 것은 **내가 제시한 그 방향**뿐이다.

## 4. 게이트 개방·잠금 (승인 후에만)

사용자의 **명시 승인**("진행해 / 좋아 / 그렇게 해")을 받은 뒤에만:

```bash
EXP=$(( $(date +%s) + 240*60 ))            # 기본 240분 = 한 작업 사이클
printf '%s\nmode=<모드> approved\n' "$EXP" > .claude/.design-unlock
```

- **승인 없이 열지 않는다.** "확인해줘 / 분석해줘" 는 승인이 아니다.
- 작업이 끝나면 **`rm -f .claude/.design-unlock`** 로 즉시 잠근다(§6 완료 보고 직후).
- 사용자가 `/design on [분]` 으로 직접 연 경우(간단·긴급)에는 이 스킬 절차를 건너뛴 것이므로,
  **최소한 ① 모드 분류 배너 하나는 남기고**(§1) 작업한다.

## 5. 구현 위임 (새 구현 에이전트를 만들지 않는다 — DRY)

| 변경 영역 | 위임 대상 |
|---|---|
| 탭 화면·서브탭 | 해당 탭 스킬/에이전트 (`vmd`·`payrate`·`inventory`·`sample-return`·`best-products`·`retail-reorder`·`wholesale-reorder`·`score-ranking`·`post-process`·`color-trend`) |
| 백엔드 구조·DB 스키마·이관 | `backend-agent` |
| 주문장 생성·배치 | `order-agent` / `batch-ingest` 스킬 |
| 새 탭 신설·iframe 제거 | `dev-blueprint` 스킬 |
| 모바일 뷰 | `mobile-view-agent` |
| 인입 포맷 방어 | `ingest-guard` 스킬 |

해당 없는 영역(공통 셸·`backend/scripts/**`·훅)만 메인이 직접 구현한다.
공유 자산(공통 계산식·config 키·공유 테이블)을 건드리면 **소비하는 쪽 에이전트도 함께** 위임한다.

## 6. 완료 보고 (작업 후 필수)

````markdown
---

### ⑦ 완료 — <결과 + 남은 리스크 유무>
`① 분류 ▸ ② 조사 ▸ ③ 설계 ▸ ④ 승인 ▸ ⑤ 구현 ▸ ⑥ 검증 ▸ 【⑦ 완료】`

> <무엇이 어떻게 됐는지 한 문장>

완료 요약:
변경 파일:
검증 결과:
- 실행한 명령:
- 결과:
영향 범위:
남은 리스크:   ← 없으면 "확인된 남은 리스크 없음"
MCP 영향:      ← 영향 없음 / 영향 있음 + 이유
````

- **검증을 돌리지 않았으면 "완료"라고 말하지 않는다**(CLAUDE.md §완료 기준). 못 돌렸으면 이유를 적는다.
- 상세 검증 체크리스트는 `post-verification` 스킬을 따른다(여기서 재서술하지 않음).
- 커밋·푸시·PR 은 **각각 별도 승인** — 완료 보고에 딸려오지 않는다.
